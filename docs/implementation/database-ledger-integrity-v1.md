# Database ledger integrity v1

This phase strengthens PostgreSQL and EF persistence boundaries around the posted financial ledger without inventing new financial policy.

## Database constraints

The generated EF migration adds structural checks that are valid for every posted journal regardless of business flow:

- each journal line is one-sided and strictly positive: either debit is positive and credit is zero, or credit is positive and debit is zero;
- a journal entry cannot be posted before its economic occurrence timestamp;
- a journal entry cannot identify itself as the journal it reverses.

These checks reject malformed persisted rows even when SQL bypasses normal application command handlers.

## Posted-history immutability

`CharkhooneDbContext` rejects tracked updates or deletes of `JournalEntryRow` and `JournalLineRow` before persistence. Corrections must be represented by a new reversal journal rather than mutation of posted history.

This is an application persistence guard. Direct SQL by a privileged database principal is outside that guard, so production runtime database privileges must separately deny UPDATE/DELETE on posted ledger tables. Database-role separation is intentionally handled as a following operational hardening phase.

## Balance boundary

The existing domain/application journal draft remains responsible for validating aggregate double-entry balance before a journal is posted. This phase does **not** claim that PostgreSQL itself enforces `sum(debit) = sum(credit)` across all lines of an entry: a row-level CHECK constraint cannot inspect peer rows, and this phase does not introduce a handwritten trigger or deferred constraint trigger.

That distinction is deliberate: the database now enforces row structure and chronology, while aggregate balance remains enforced by the existing journal-construction path and tested application behavior.

## Verification

Tests cover:

- modification of a tracked posted journal entry is rejected before database write;
- deletion of a tracked posted journal line is rejected before database write;
- PostgreSQL rejects a two-sided journal line through the generated CHECK constraint;
- PostgreSQL rejects a journal header whose posting timestamp precedes its occurrence timestamp.

The migration is generated by `dotnet ef`; historical generated migrations are not edited.

## Deployment boundary

This phase does not apply the migration to staging or production. It must use the existing staging-first migration runbook, backup/PITR gate, post-migration verification, and forward-fix strategy before production deployment.

No lost-fund-return day-count, rounding, partial-allocation rule, or early-cancellation frozen-principal release rule is encoded here.
