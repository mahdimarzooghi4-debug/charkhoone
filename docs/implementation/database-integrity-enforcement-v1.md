# Database integrity enforcement v1

Baseline: constraint/integrity audit PR #39 at `a8c4de2e4a7ed49e9eab004bf7c0aafc45061e19`.

This phase turns deterministic findings from the read-only audit into relational enforcement. It does not define unresolved financial policy and it is not a staging/production migration record.

## Enforced in the EF model

- `frozen_principals.ContractId` now references `lease_contracts.Id` with restrictive deletion.
- nullable `lease_contracts.CreditApplicationId` now references `credit_applications.Id` with restrictive deletion.
- journal-line deletion no longer cascades when a journal header is deleted; the journal-entry relationship is restrictive.
- journal lines must contain exactly one strictly positive side and neither side may be PostgreSQL numeric `NaN`/`Infinity`.
- journal posting time cannot precede economic occurrence time, and an entry cannot reverse itself.
- ledger-account and external-transaction currency is constrained to canonical `IRR`.
- journal/external-transaction/payment/fund-freeze idempotency keys covered in this slice cannot be whitespace-only.
- payment instructions require a positive finite amount.
- Frozen Principal requires a positive finite amount and nonblank bank/fund references.
- bank approval amounts are finite/nonnegative, and a populated approved amount must be positive and no greater than the recorded eligibility ceiling.
- funding allocation enforces the already-existing approved-loan rule: approved loan is positive, no greater than either the eligibility ceiling or full-deposit equivalent, and `TenantContributionRial = FullDepositEquivalentRial - BankApprovedLoanRial` with nonnegative finite inputs.

These are persistence invariants already required by current domain/application behavior; they do not add a new day-count, rounding, partial-payment, settlement, or cancellation policy.

## Posted ledger protection boundary

`CharkhooneDbContext` rejects tracked UPDATE/DELETE changes to `JournalEntryRow` and `JournalLineRow`; corrections continue through new reversal journals. PostgreSQL also prevents deleting a journal header while lines exist and rejects malformed journal lines.

A database owner/superuser can still issue a direct SQL UPDATE to otherwise-valid journal fields, and a privileged user can still delete individual journal lines. The integrity audit continues to detect cross-row imbalance. Therefore this phase does **not** claim that privileged SQL has been made impossible. Runtime database-role/grant hardening is the next enforcement boundary: the application role must not own the schema and must not receive UPDATE/DELETE on posted-ledger tables.

## Verification

Integration tests exercise the migrated PostgreSQL constraints directly, including malformed journal amounts, canonical currency, blank journal idempotency, orphan Frozen Principal and funding-allocation equation mismatch. Persistence-model tests verify the new foreign keys, restrictive delete behavior, check constraints, and the tracked-mutation guard.

The existing source/restored financial audit remains in CI. The backup/restore drill must still pass after this migration so recovery evidence covers the hardened schema.

## Deployment boundary

The EF migration for this phase must be generated by the real `dotnet ef` CLI and reviewed before use. It is not evidence that any staging or production database has been changed. Before an authorized environment migration, run the existing read-only integrity audit against that environment; any pre-existing violating row must be investigated and remediated explicitly rather than hidden by editing historical migrations or mutating posted ledger history.

Lost-fund-return day-count/accrual/rounding/partial allocation and early-cancellation Frozen Principal release timing remain undefined and untouched.
